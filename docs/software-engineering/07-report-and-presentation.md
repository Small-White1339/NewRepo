# 报告与答辩使用指南

本文件帮助把工程材料包整理成课程最终作业。它不宣称已经生成 Word、PPT 或完成真实调研。建议先完成 [课程要求对照](00-course-checklist.md) 中的缺口，再排版，而不是先依靠插图凑满页数。

## 30 页以上报告建议结构

以下是 **32 页正文的建议分配**，不含封面、目录、参考文献和附录。实际页数取决于学校模板、字体、图表与内容，应在最终排版后核对。

| 章节 | 建议页数 | 主要内容与材料 | 适合插入的图 |
|---|---:|---|---|
| 1 项目概述 | 2 | 开发目的、用户场景、产品边界、上游与本组增量 | F01 |
| 2 可行性分析 | 3 | 技术、经济、操作、法律与政策来源 | 已验证事实与真实调研表 |
| 3 需求分析 | 6 | 顶级需求、角色、功能与非功能需求、典型用例 | F04–F08、F14 / F15 |
| 4 概要设计 | 4 | 系统分层、模块职责、软件结构、网络边界 | F01–F03、F17 / F18 |
| 5 数据库与接口设计 | 4 | ER、字段字典、约束、接口与数据量分析 | F09 / F10 |
| 6 详细设计 | 4 | 匹配、图片解析、Agent 输入输出与失败路径 | F11–F13、F16 / F19 |
| 7 编码实现与 UI | 3 | 关键实现片段、页面说明、原文与报告展示 | F22 与实际运行截图 |
| 8 测试与质量 | 3 | 黑盒、白盒、结果、缺陷修复与未覆盖项 | 实际测试输出或记录 |
| 9 项目管理 | 2 | WBS、真实计划、配置管理、分工与报价 | F20 / F21 |
| 10 总结与展望 | 1 | 当前成果、限制、后续实现需求 | 不新增未经验证的能力 |
| 合计 | **32** | 正文建议，不是已排版页数 | — |

图表多不等于分析充分。每张图至少交代“图的类型、对象、关键关系和设计含义”；复杂图可用横向页面或分图，避免缩到文字无法阅读。F02 为宽幅结构图，F10 为纵向 ER 图，F05 信息量较大，优先使用 SVG。

## 实现截图与演示顺序

| 编号 | 需采集的真实画面 | 证明什么 | 数据要求 |
|---|---|---|---|
| UI01 | 注册角色选择与登录 | 软件确有双角色入口 | 不展示真实密码或令牌 |
| UI02 | HR 首页与岗位管理 | HR 资源管理与来源标记 | 演示岗位或公开来源 |
| UI03 | 上传照片、原文与结构化资料 | OCR 与 AI 的分工及人工核对 | 虚构演示简历或明确来源的公开资料 |
| UI04 | HR 选择岗位和多份简历匹配 | 批量入口和逐项结果 | 不使用私人候选人信息 |
| UI05 | HR 报告与失败提示 | 评分、说明、失败不伪造分数 | 标明测试数据 |
| UI06 | 求职者首页与岗位探索 | 与 HR 不同的导航与使用目标 | 本地求职者演示账号 |
| UI07 | 个人匹配三项分数和准备建议 | 个人岗位适配和行动建议 | 标明公开参考简历不是真实投递 |
| UI08 | 收藏、备注、进度和刷新后的结果 | 私有数据持久化 | 不声称“面试中”由招聘方确认 |
| UI09 | 我的求职中的历史报告与排序 | 可再次查询已有结果 | 避免只拍空列表 |
| CM01 | GitHub 提交记录与变更 | 配置管理与团队增量 | 不拍 .env 内容 |
| TEST01 | 自动化测试完整结果 | 实际测试执行 | 保留命令、版本和日期 |

可先演示 HR 的“导入岗位→管理资料→批量匹配”，再退出并切换求职者，演示“上传个人简历→探索岗位→个人匹配→收藏进度”。模型调用可能耗时，答辩时可以先展示已完成且有来源的报告，再展示一次小规模实际操作；不要用假结果替代实际模型输出。

## PPT 建议结构

建议 12–15 页，具体时长按老师要求调整：

1. 项目名称、真实成员与职责。
2. 用户问题、目标与范围。
3. HR / 求职者两类角色与用例摘要，F07 / F08。
4. 顶层与一层 DFD 的重点，F04 / F05，可拆成两页。
5. 总体架构与模块职责，F01 / F02。
6. 数据库核心关系，F10，完整字段放附录。
7. AI 流水线与角色化报告，F19。
8. 照片解析、数据去向和失败处理，F13 / F16。
9. HR 功能实际截图。
10. 求职者功能实际截图。
11. 一个典型顺序图与状态图的关键分支，F12 / F14。
12. 黑盒、白盒测试与真实结果。
13. 项目计划、Git 配置管理、真实分工与报价摘要。
14. 限制、后续工作与答辩总结。

每页只说明一个主要结论，不要把全部 22 张图缩成一页。DFD 用于说明数据边界，顺序图说明时序，状态图说明对象状态，回答问题时要指出区别。

## 常见答辩问题与事实提示

| 问题 | 回答应包含的事实 |
|---|---|
| 为什么需要 Agent，是否真正多智能体自治？ | 有 5 个职责不同的业务 Agent 类，每次执行 4 步；当前是固定编排，没有自主工具选择和向量检索 |
| OCR 与 DeepSeek 分别做什么？ | 本地 OCR 从图片取文字；DeepSeek 分析文字与岗位说明，原图片不随该调用上传 |
| 求职者和 HR 能否查看彼此资料？ | 简历和报告按账号归属隔离；ACTIVE 岗位可供求职者探索；个人匹配不自动共享给岗位发布者 |
| 分数是否代表录用概率？ | 不代表；是模型基于文本的适配参考，需要人工核对 |
| 真实岗位与简历从哪里来？ | 固定 Lever 公司来源与 JSON Resume 用户来源；保留链接和采集时间，公开履历不等于平台投递 |
| “面试中”和“收到录用”从哪里来？ | 本人手动记录；没有招聘方回调或站内申请流程 |
| 为什么保存原文与 JSON 又建子表？ | 原文用于证据核对，JSON 保留分析结果，子表便于结构化展示和维护；存在重复存储成本 |
| HTTP 201 为什么还可能失败？ | 201 表示报告资源已创建，AI 成功与否看 status；FAILED 没有成功分数 |
| 是否已部署生产环境？ | 本地运行已验证；Docker 图是仓库配置方案，容器与 PostgreSQL 端到端仍需单独验收 |
| 哪些代码是本组做的？ | 按 UPSTREAM、Git 基线和真实分工说明继承内容与增量，不把全部项目归为从零开发 |

## 引用与最终检查

引用代码建议写提交号、仓库相对路径和关键函数；引用公开数据写来源 URL 与访问日期。图表注明“根据代码基线 e92e561 整理”；若后续功能改变，应重新导出与核对。

本包可直接复用的内容是模块职责、代码参考、图表、需求与测试设计。仍需项目组亲自补齐的是实际用户组织与政策依据、真实组员贡献、实际计划和工时、报价来源、软件截图，以及最终报告和 PPT 的排版与演示。
